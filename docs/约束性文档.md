# 知衡约束性文档

> 本文档是项目开发的**硬性约束**，优先级高于一般代码习惯。
> 违反本文档的变更应被拒绝。随架构决策更新。

---

## 1. 医疗安全（最高优先级，§3、§60）

1. **禁止编造医学结论**。医学规则必须有依据：临床指南 / 专家共识 / 药品说明书 / 医生制定的方案。
2. **禁止硬编码剂量与治疗频率为医学事实**（§4）。光疗剂量、治疗频率、疗程周期必须来自医生方案或已收录的知识库条目；代码中出现的默认值（如每周一三五）必须能在知识库中找到出处，且 UI 必须提示「以医生方案为准」。
3. **AI 不决策**（§61）：AI 只解释/总结/整理，不诊断、不修改处方、不决定剂量。
4. **不确定的医学问题不猜**：标注「需要医学依据」并提供来源要求。
5. 优先级：医疗安全 > 数据正确性 > 用户可理解性 > 可维护性 > 可访问性 > 性能 > 视觉效果 > 开发速度（§60）。
6. **血糖监测只做记录，不自动调整治疗**（v1.9.0 新增）：
   - 血糖读数（空腹/餐后2小时/睡前等）仅做数据沉淀，APP 不根据血糖值自动推荐胰岛素剂量或口服药调整。
   - 低血糖自动标记（<3.9 mmol/L 标黄、<3.0 mmol/L 标红）属于「数据整理与风险提示」，依据《中国糖尿病防治指南（2024版）》分级；标记后文案仅为「建议关注/建议联系医生」，不给出具体处理指令（如「吃多少糖」「减少多少胰岛素」）。
   - 血糖趋势分析（如「最近餐后血糖升高较频繁」）属于「统计观察」，不得自动得出「你应该减少碳水」等治疗建议。
   - 必须咨询医生的情况（反复低血糖、<3.0 mmol/L、持续明显升高等）应统一提示「建议就医评估」，不自行解释病因。


## 2. 数据正确性

1. **历史不可变（§44）**：历史事件/记录不被当前方案覆盖。方案调整用新增（计划 v2 替代 v1），任务完成事件用追加。
2. **更正而非改写**：用户主动撤销视为更正（删除刚产生的完成事件），但不得改写已发生的历史事实本身。
3. **任务来源可追踪（§10）**：Task.source 必须明确（医生方案/临床规则/管理计划/用药计划/监测计划/自建），不得笼统归为 AI。模板创建的任务必须带 templateId。
4. **数据结构化优先于 AI（§61）**：先有可靠数据模型，再谈智能。

## 3. 架构约束（§17、§18、§19、§46）

1. Feature-based 架构：`lib/{app,core,features,shared}`；禁止巨型 widgets/ 或 services/ 目录。
2. **分层**：UI → Notifier → Repository → Drift。UI 不直接操作 Repository 以外的存储细节；业务逻辑禁止写在 Widget 中。
3. 医学规则与 UI 分离（§12）：Flutter Widget 中禁止出现 `if (bloodSugar > xxx)` 这类医学判断；规则必须位于独立业务层。
4. 领域模型（Domain）与 DTO 分离（§41）：UI 使用领域模型；未来 API 变化不波及 UI。
5. **状态管理统一 Riverpod**；Provider 可测试；Async 状态明确。
6. 修改公共接口（Repository 方法、领域模型）前必须检查全部调用方（§46）。
7. 禁止创建 God Class / 巨型 Service / 重复实现（API Client、Theme 等）。

## 4. 依赖约束

1. **不随意引入第三方依赖**；引入前评估必要性（一个简单功能不得引入大型框架）。
2. 依赖变更必须同步更新《功能文档》与《更新文档》。
3. Flutter 版本由 mise.toml 锁定，本地与 CI 保持一致（GitHub Actions 用 mise-action）。

## 5. 数据与隐私（§35、§36）

1. 患者数据最小化收集；本地敏感数据放应用私有目录。
2. 禁止在日志中输出：姓名、手机号、身份证、病历、完整医疗记录、照片路径、Access Token。
3. 调试日志不得输出完整医疗数据。
4. 未来第三方 AI 调用前必须生成脱敏的 AI Context（§36），不直接发送完整数据库；数据授权可撤销（§15）。

## 6. 代码质量（§56）

1. Null Safety、强类型、小函数、小 Widget、单一职责、明确命名。
2. 避免魔法数字/字符串（用 Tokens 与常量）。
3. 公共组件必须有文档注释。
4. 核心 Domain 必须有测试；医学规则必须有独立测试（§43：正常/边界/异常/缺失数据/版本升级）。
5. 禁止 TODO 掩盖未完成核心功能；禁止用 Mock 数据伪装真实功能。

## 7. 测试约束（§42）

1. 每个功能切片至少覆盖：正常路径 + 空状态 + 错误状态。
2. Widget 测试中 drift 真实异步必须用 `tester.runAsync` 包裹。
3. 禁止删除已有测试；修改行为必须同步更新受影响测试。

## 8. 文档约束（§57）

1. 每次功能变更：更新《功能文档》；发布版本：追加《更新文档》（只追加不改写）。
2. 架构/规则变更：更新本文档；Design System 变更：更新《UI 风格文档》。
3. 数据模型变更：更新《数据模型文档》；知识库变更：更新《医学知识库》。

## 9. 版本管理

版本号格式：`major.minor.patch+build`（pubspec.yaml 的 `version` 字段）。

### 9.1 版本递增约束

| 变更类型 | 判定标准（满足任一即升级该位） | 示例 |
|---|---|---|
| **大功能迭代 → major+1** | ① 破坏性架构变更（分层/数据流重构）；② schema 迁移不兼容（删列/改列语义）；③ 跨产品线能力（AI、FHIR、医生端）；④ 行为不兼容变更 | 1.7.0 → 2.0.0 |
| **中等功能迭代 → minor+1** | ① 新增用户可见功能模块；② schema 向后兼容迁移（加表/加列）；③ 跨页面/跨模块功能集 | 1.7.0 → 1.8.0 |
| **小功能迭代 → patch+1** | ① 单点功能增强；② bug 修复；③ UI 微调；④ 文案/文档；⑤ 依赖小版本升级 | 1.7.0 → 1.7.1 |
| **build → +N** | 每次发版必须递增（Android versionCode / iOS build number，商店要求单调递增） | 1.7.0+8 → 1.7.0+9 |

### 9.2 判定细则

1. **schema 变更分档**：向后兼容（`m.addColumn` / `m.createTable`）→ minor；破坏性（删列、改枚举语义、重写迁移）→ major。
2. **新功能分档**：一个完整功能模块（如光疗记录）→ minor；该模块内的单个交互增强（如「添加按钮」）→ patch。
3. **修复分档**：修复已发布 bug → patch；修复过程改变公共接口 → 视破坏性程度 minor 或 major。
4. **同时包含多档变更时按最高档执行**（如既有 minor 又有 patch → 按 minor 发版）。
5. **首次发布**：从 1.0.0 开始；0.x 表示未稳定（当前已过此阶段）。
6. **build number 独立递增**：同一次发版中版本号与 tag 必须一致；重新打包（补发）时仅 build+1，tag 不变。

### 9.3 发版前检查

1. 对照 9.1 判定本次变更档位 → 确定升哪一位。
2. 版本号必须与 git tag 一致（`v1.8.0` ↔ `version: 1.8.0+9`）。
3. build number 必须大于上一个 tag 的 build number。
4. 同步更新 docs/更新文档.md（追加「最新版本」条目）。

## 10. 发布流程

1. `flutter analyze` 无问题 + `flutter test` 全过 → 按「版本管理」升版本 → 更新 docs/更新文档.md。
2. 运行 `bash tool/check_release.sh` 校验版本号与 tag 一致性（大/中/小档位判定 + build 递增）。
3. commit → push → `git tag vX.Y.Z && git push origin vX.Y.Z`。
4. tag 触发 GitHub Actions：CI（analyze+test）→ Build Android（APK/AAB + Release 附件）→ Build iOS（未签名验证包）。
   - **Release 附件命名**：附件以「项目标识-版本含build-架构」命名，带 `+build` 便于同版本补发区分。APK 分两类：
     - 通用整包 `zhiheng-<version>-universal.apk`（含 arm64-v8a / armeabi-v7a / x86_64 全部 ABI，适合直接安装，兼容所有设备）；
     - 按 ABI 拆包（`flutter build apk --release --split-per-abi`）`zhiheng-<version>-arm64-v8a.apk`、`zhiheng-<version>-armeabi-v7a.apk`、`zhiheng-<version>-x86_64.apk`（单架构，体积约为整包的 1/3～1/2；主流手机选 arm64-v8a）。
     - AAB 命名 `zhiheng-<version>.aab`（架构无关）。
     - 禁止发布 gradle 默认名（`app-release.apk` / `app-release.aab`）。
   - **CI 触发策略**：`ci.yml` 仅 `main` push 与 PR 触发，且 `paths-ignore` 跳过纯文档变更（`docs/**`、`**/*.md`——文档提交不跑 CI）；Android/iOS 打包仅 `v*` tag 或手动（workflow_dispatch）触发，不随普通提交跑。
   - **Actions 版本策略**：跟随 GitHub Node 24 运行时（checkout@v5 / setup-java@v5 / upload-artifact@v6 / mise-action@v4 / gh-release@v3 / setup-xcode@1.7+）；升级前需先确认目标版本的 `action.yml` 运行时（node24）与所用输入项兼容，禁止盲跳大版本。
5. **Android release 必须使用正式签名**：本地 `android/key.properties`（key 文件 `android/app/upload-keystore.jks`）与 CI Secrets（`ANDROID_KEYSTORE_BASE64`/`ANDROID_KEYSTORE_PASSWORD`/`ANDROID_KEY_PASSWORD`/`ANDROID_KEY_ALIAS`）配置同一把 key，保证本地安装包与 CI Release 签名一致、覆盖升级不冲突。
   - **禁止回退 debug 签名出 release 包**（gradle 无 key.properties 时构建直接失败）：debug 证书随构建机生成、每次 CI 运行都不同。历史 v1.0–v1.6 曾因此误发 debug 签名包，导致用户覆盖安装全部报「签名不正确」，只能卸载重装。
   - keystore 与 key.properties 不入库（android/.gitignore 已忽略）；keystore base64 与口令需单独离线备份（具体存放路径不入仓库文档，仅由维护者离线自行保管）。
   - **签名凭据必须实测验证后再使用**：改动 keystore / key.properties / Secrets 后，先本地 `keytool -list -v -keystore <keystore> -storepass <口令>` 确认能打开且证书 subject=`CN=Zhiheng`，再用与 AGP 相同的 `KeyStore.load` 校验，最后才同步备份文件与 GitHub Secrets；备份文件与 4 个 Secrets 必须同源同值。
   - **base64 必须完整单行复制**：`ANDROID_KEYSTORE_BASE64` 为 2992 字符单行（结尾 `3Q==`）；GitHub Secret 值不要手动换行，截断/换行会触发 `base64: invalid input`，CI 在签名前置步骤直接失败。
   - 历史教训（2026-09-02/03）：首次生成的 keystore 与记录口令不匹配（`KeyStore.load` 报 `Keystore was tampered, or password was incorrect`、JKS 摘要校验不通过），导致 v1.8.0 Build Android 在签名步失败；同日 base64 复制截断又触发 `invalid input`。已重新生成官方 keystore（CN=Zhiheng，SHA-256 `20:42:41:94:…:26`）并同步备份与 Secrets，为现行签名。
   - 用户手机若装有旧版（不同签名），升级到 v1.8.0 前需先卸载一次旧版；此后所有版本共用同一正式 key，可平滑更新。
